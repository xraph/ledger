Ledger is one engine, `ledger.Ledger`, in front of one storage interface, `store.Store`. The engine holds the billing rules: validation, quota checks, pricing, invoice assembly and the subscription lifecycle. Each entity package (`plan`, `subscription`, `invoice` and so on) defines a model and its slice of the store interface. The stores persist those models, and plugins hook into what the engine does.

## Package diagram

```
ledger.Ledger
  plans          CreatePlan, UpdatePlan, ActivatePlan, ArchivePlan, DeletePlan
  catalog        CreateFeature, UpdateFeature, ArchiveFeature, ListFeatures
  subscriptions  CreateSubscription, ChangePlan, PauseSubscription,
                 ResumeSubscription, CancelSubscription
  usage          Meter, Entitled, Remaining, InspectEntitlement
  invoices       GenerateInvoice, FinalizeInvoice, MarkInvoicePaid,
                 MarkInvoiceVoided, ExportInvoice
  coupons        CreateCoupon, ApplyCoupon, ListAppliedCoupons
  providers      Sync*ToProvider, Import*FromProvider, HandleWebhook
  lifecycle      Advance (periods, cancels, trials, past-due invoices)
      │
      ├── plugin.Registry      typed hooks (OnPlanCreated, OnInvoicePaid, ...)
      │                        strategy plugins (pricing, aggregation, tax,
      │                        export formats, coupon validation, providers)
      │
      ├── background workers   meter flush (batch size or interval)
      │                        lifecycle clock (Advance every minute by default)
      │
      └── store.Store          plans, catalog features, subscriptions, usage,
                               entitlement cache, invoices, coupons and their
                               applications, lifecycle queries,
                               Migrate, Ping, Close
            │
            ├── store/postgres ─┐
            ├── store/sqlite   ─┼─ on a *grove.DB
            ├── store/mongo    ─┘
            └── store/memory
```

The diagram is a summary. "Sync\*ToProvider" stands for `SyncPlanToProvider`, `SyncFeatureToProvider`, `SyncSubscriptionToProvider` and `SyncInvoiceToProvider`, and the import methods follow the same pattern. [Go packages](/docs/api-reference/go-packages) has the full list.

## Engine construction

`ledger.New` takes the store and functional options:

```go
engine := ledger.New(store,
	ledger.WithMeterConfig(100, 5*time.Second),     // batch size, flush interval
	ledger.WithEntitlementCacheTTL(30*time.Second), // quota answer cache
	ledger.WithLifecycleInterval(time.Minute),      // 0 turns the clock off
	ledger.WithPlugin(auditPlugin),
	ledger.WithLogger(logger),                      // a go-utils log.Logger
)
```

There's no `WithProvider`: a payment provider is a plugin that implements `plugin.PaymentProviderPlugin`. [Configuration](/docs/concepts/configuration) lists every option.

## The billing flow

1. You create plans. Each plan lists its features, a currency, a base fee and price tiers per feature. A plan starts as a draft and takes subscribers once it's active.
2. You subscribe a tenant. The engine sets the first period from the plan's billing period and starts a trial if the plan has trial days.
3. Your request path calls `Entitled` before the work and `Meter` after it.
4. You call `GenerateInvoice` for a period. It reads usage from the store, prices it against the plan's tiers, subtracts applied coupons and adds tax from any tax plugin.
5. You finalize the invoice and, once your payment provider has collected, mark it paid.

Ledger never charges a card and never generates an invoice by itself. Steps 4 and 5 are calls you make, from your own scheduler or from a plugin hook such as `OnSubscriptionRenewed`.

## Background work

`Start` runs two goroutines. Both stop on `Stop`.

### Meter flush worker

```
Meter() ──> buffered channel (10,000 events) ──> worker batch
                                                   │
                         batch full ───────────────┤
                         flush interval ticks ─────┴──> store.IngestBatch
```

`Meter` returns as soon as the event is on the channel, or with `ErrMeterBufferFull` when the channel is full. The worker writes a batch when it reaches the batch size or when the interval ticks. A batch that fails to write is logged and dropped. On `Stop`, the worker writes the batch it holds.

### Lifecycle clock

Every interval (one minute by default) the clock calls `Advance(ctx, now)`, which runs four steps in order:

1. `AdvancePeriods` moves every active, trialing or past-due subscription whose period has ended into the period that contains now.
2. `EnactCancels` cancels subscriptions whose scheduled cancel date has passed.
3. `EndTrials` makes trialing subscriptions active once their trial ends.
4. `MarkInvoicesPastDue` moves pending invoices past their due date to `past_due`.

Every change is a conditional store write, so several replicas can run the clock at once and only one of them reports each change and fires its hook. Turn the clock off with `WithLifecycleInterval(0)` and call `Advance` yourself if you'd rather drive it from your own scheduler.

## Quota checks

```
Entitled(ctx, key) ──> store.GetCached ──hit──> return
                            │ miss
                            v
         active subscription ─> plan ─> feature ─> store.Aggregate
                            │
                            v
                   store.SetCached(ttl) ──> return
```

The cache lives in the store: a table in PostgreSQL and SQLite, a collection in MongoDB, a map in the memory store. Entries are keyed by tenant, app and feature. The engine clears a tenant's entries when its subscription is created, changed, paused, resumed, canceled or moved by the lifecycle clock. Metering doesn't clear them, so a quota answer can lag new usage by up to the TTL.

## Tenancy

Two identifiers scope the data. `TenantID` is the customer you bill, and it's set on subscriptions, usage events and invoices. `AppID` is the product or deployment, and plans, catalog features, coupons, subscriptions, usage and invoices all carry it. `Entitled`, `Remaining` and `Meter` read both from the context values `"tenant_id"` and `"app_id"`. Lookups by ID don't check either. See [Multi-tenancy](/docs/concepts/multi-tenancy).

## Plugins

A plugin implements `plugin.Plugin`, which is only `Name() string`, plus any hook interfaces it wants:

```go
type Plugin interface {
	Name() string
}

type OnInvoiceGenerated interface {
	Plugin
	OnInvoiceGenerated(ctx context.Context, inv interface{}) error
}
```

Hooks are synchronous: the call that fires them waits for each plugin in turn, and most fire after the store write has landed. Each hook gets five seconds. An error or a timeout is logged, counted on `ledger_plugin_hook_failures_total` when the engine has metrics, and never fails the operation. The module ships two plugins, `audit_hook` and `observability`. See [Custom plugin](/docs/guides/custom-plugin).

## Money

`types.Money` is an amount in the currency's smallest unit and a lowercase ISO 4217 code:

```go
price := types.USD(4999)            // $49.99
seats := types.USD(1000).Multiply(3) // $30.00
total := price.Add(seats)            // $79.99, panics if the currencies differ
fmt.Println(total.String())          // "$79.99"
fmt.Println(total.FormatMajor())     // "79.99"
```

`CheckedAdd`, `CheckedSubtract`, `CheckedMultiply` and `CheckedPercent` return an error wrapping `types.ErrOverflow` instead of wrapping around. Invoice generation uses them for every sum.

## TypeIDs

Every entity ID is a [TypeID](https://github.com/jetify-com/typeid): a prefix, an underscore and a base32 UUIDv7, so IDs sort by creation time.

```
plan_01h455vb4pex5vsknk084sn02q   plan
feat_01h455vb4pex5vsknk084sn02q   feature
sub_01h455vb4pex5vsknk084sn02q    subscription
inv_01h455vb4pex5vsknk084sn02q    invoice
cpn_01h455vb4pex5vsknk084sn02q    coupon
uevt_01h455vb4pex5vsknk084sn02q   usage event
```

[Identity](/docs/concepts/identity) has the full prefix list.
