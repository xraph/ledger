A plan is what you sell. It lists the features a subscriber gets, each with a limit, and the pricing: a base fee per billing period plus price tiers for the features that bill by usage or by seat. Quota checks and invoices both read the same plan, so the limit you enforce is the allowance you bill against.

```go
pro := &plan.Plan{
	Name:      "Pro",
	Slug:      "pro",
	Currency:  "usd",
	Status:    plan.StatusActive,
	AppID:     "my-app",
	TrialDays: 14,
	Features: []plan.Feature{
		{Key: "api_calls", Name: "API calls", Type: plan.FeatureMetered, Limit: 10000, Period: plan.PeriodMonthly, SoftLimit: true},
		{Key: "seats", Name: "Seats", Type: plan.FeatureSeat},
		{Key: "sso", Name: "Single sign-on", Type: plan.FeatureBoolean, Limit: 1},
	},
	Pricing: &plan.Pricing{
		BaseAmount:    types.USD(4900),
		BillingPeriod: plan.PeriodMonthly,
		Tiers: []plan.PriceTier{
			{FeatureKey: "api_calls", Type: plan.TierGraduated, UpTo: 10000, UnitAmount: types.Zero("usd")},
			{FeatureKey: "api_calls", Type: plan.TierGraduated, UpTo: -1, UnitAmount: types.USD(1)},
			{FeatureKey: "seats", Type: plan.TierGraduated, UpTo: -1, UnitAmount: types.USD(1000)},
		},
	},
}
if err := engine.CreatePlan(ctx, pro); err != nil {
	return err
}
```

[Entities](/docs/concepts/entities#plan) has every field.

## Features

Each plan feature has a `Key`, which is what `Entitled` and `Meter` name, and a `Type`:

| Type | Quota check | Invoice |
|------|-------------|---------|
| `plan.FeatureMetered` | Usage in the quota window against `Limit` | Usage past `Limit` in the billed period, priced through the feature's tiers |
| `plan.FeatureSeat` | Same as metered: usage events recorded under the key, against `Limit` | Every seat in `Subscription.Quantity[key]`, priced through the tiers. `Limit` isn't used |
| `plan.FeatureBoolean` | Allowed when `Limit` is above 0 | Nothing |

`Limit` is `-1` for unlimited. A metered feature with `-1` never bills overage. `SoftLimit: true` lets usage pass the limit: the check still allows the request, with the reason `"over soft limit"`. Without it, the check denies with `"quota exceeded"`.

`Period` sets the quota window for the check: `plan.PeriodMonthly` counts usage since the start of the current UTC calendar month, `plan.PeriodYearly` since the start of the year, and `plan.PeriodNone` or an empty period counts all usage ever recorded. The window doesn't follow the subscription's billing period, and invoices ignore it: an invoice always counts the usage inside the period it bills.

## Pricing

`Pricing` is optional. A plan without it bills nothing.

- `BaseAmount` is charged once per billed period. Its currency must match the plan's, and an empty currency takes the plan's.
- `BillingPeriod` decides how long a subscription's period is: `plan.PeriodMonthly` (the default when empty) or `plan.PeriodYearly`. `plan.PeriodNone` gives a first period of one month and then never rolls it.
- `Tiers` price metered overage and seats, per feature key.

### Tier models

All tiers for one feature must share a `Type`. `UpTo` is the total usage a tier reaches in the period, not the usage past the allowance, and `0` or `-1` marks the open-ended top tier. A ladder without an open-ended tier extends its last tier to cover everything above it.

For a metered feature, the invoice charges `price(usage) - price(allowance)`, where the allowance is the feature's `Limit`. That way a `$0` first tier for the allowance is never charged twice.

Graduated tiers (`plan.TierGraduated`) charge each unit at the rate of the tier it falls in. With tiers of 0 cents up to 10,000, 2 cents up to 50,000 and 1 cent above, and a limit of 10,000, usage of 10,650 bills 650 units at 2 cents: $13.00.

Volume tiers (`plan.TierVolume`) find the tier that total usage reaches and apply its rate to every billable unit. With tiers of 3 cents up to 50,000 and 2 cents above, a limit of 10,000 and usage of 60,000, the invoice bills 50,000 units at 2 cents: $1,000.00.

Flat tiers (`plan.TierFlat`) charge the `FlatAmount` of the tier that usage reaches, less the fee for the tier the allowance sits in. Flat tiers carry no `UnitAmount`.

Seat features price the full seat count with an allowance of zero, so for seats a single open-ended graduated tier is a plain per-seat price.

### Validation

`CreatePlan`, `UpdatePlan` and `ActivatePlan` validate the plan before writing it. They refuse:

- a missing name, slug or currency, or an unknown status;
- negative trial days;
- a feature without a key, a duplicate key (`ErrDuplicateFeature`), an unknown type or period, or a limit below `-1`;
- a negative base price, or one in another currency (`ErrInvalidPricing`);
- a tier for a feature the plan doesn't have (`ErrInvalidPricing`);
- a broken credit pool (`ErrInvalidCreditPool`), covered above;
- a broken ladder (`invoice.ErrInvalidTiers`): mixed types, an unknown type, a currency that isn't the plan's, two tiers with the same `UpTo`, a negative amount, a graduated or volume tier with a `FlatAmount`, or a flat tier with a `UnitAmount`.

`CreatePlan` also trims the name and slug, lowercases the currency, gives features and pricing their IDs, and refuses a slug the app already uses (`ErrAlreadyExists`).

### Custom pricing

A feature (or the whole plan) can name a pricing strategy plugin in its `Metadata` under `"pricing_strategy"`, and a metered feature can name a usage aggregator under `"aggregator"`. The engine hands the pricing or the usage total to that plugin. See [Custom plugin](/docs/guides/custom-plugin#strategy-plugins).

## Credit pools

A credit pool is an amount of usage a plan covers each billing period, in money rather than units. Give a plan a pool and its invoice takes that much off the metered charges for the features the pool names.

```go
pro.Credits = []plan.CreditPool{
	{Key: "ai", Amount: types.USD(2000), FeatureKeys: []string{"api_calls"}},
}
```

Each pool becomes one negative `credit` line on the invoice, titled "<key> credit". The credit is the smaller of the pool's amount and the usage charges already on the invoice for its features, so a pool only ever cancels usage. It never touches the base fee or seat charges, it never goes below zero, and a pool with no usage to cancel adds no line. Unused credit doesn't roll over. The sum of the credits is `Invoice.CreditAmount`.

Credit comes off before coupons. A percentage coupon is taken on the subtotal less credit.

A pool needs a unique key, an amount above zero in the plan's currency, and feature keys that exist on the plan and are metered. A feature can sit in one pool at most, so a unit of usage is never paid for twice. `CreatePlan`, `UpdatePlan` and `ActivatePlan` refuse anything else with `ErrInvalidCreditPool`.

## Status

| Status | Meaning |
|--------|---------|
| `plan.StatusDraft` | The default. Can't take subscribers. |
| `plan.StatusActive` | Takes subscribers. |
| `plan.StatusArchived` | Takes no new subscribers. Existing subscriptions keep billing. |

```go
engine.ActivatePlan(ctx, planID) // validates, then makes it active
engine.ArchivePlan(ctx, planID)  // stops new subscriptions
engine.DeletePlan(ctx, planID)   // only when no subscription uses it, or ErrPlanInUse
```

Activating an active plan, or archiving an archived one, does nothing.

## Updating a plan

`UpdatePlan` saves the plan you pass. The app and currency can't change once the plan exists, and a new slug must be free in the app. Every subscriber sees the change in their next invoice, and in quota checks once their cached answers expire: Ledger keeps no history of plans, and an invoice prices a period with the plan as it is when you generate it.

## Reading plans

```go
p, err := engine.GetPlan(ctx, planID)
p, err = engine.GetPlanBySlug(ctx, "pro", "my-app")
plans, err := engine.Store().ListPlans(ctx, "my-app", plan.ListOpts{Status: plan.StatusActive})
```

## The feature catalog

The catalog (`feature.Feature`) is a separate list of reusable feature definitions, per app or global (`AppID: ""`). The dashboard uses it to build plans. A plan feature can point at one through `CatalogID`, but quota checks and invoices only read the plan's own `Features`.

```go
f := &feature.Feature{Key: "api_calls", Name: "API calls", Type: feature.FeatureMetered, DefaultLimit: 10000, AppID: "my-app"}
if err := ledger.ValidateFeature(f); err != nil { // CreateFeature doesn't validate
	return err
}
if err := engine.CreateFeature(ctx, f); err != nil {
	return err
}
```

The engine also has `GetFeature`, `GetFeatureByKey`, `ListFeatures`, `ListGlobalFeatures`, `UpdateFeature`, `ArchiveFeature` and `DeleteFeature`.

## Remote access

Ledger has no HTTP routes for plans. The Forge dashboard reaches them through the contract intents `plans.list`, `plans.detail`, `plans.create`, `plans.update`, `plans.archive`, `plans.activate` and `plans.delete`. See [HTTP API](/docs/api-reference/http-api).
